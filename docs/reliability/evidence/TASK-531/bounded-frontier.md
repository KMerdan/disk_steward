This is implementation evidence for AC-TASK-531-01, not gate approval, and does not close FIND-SCALE by itself.

## What changed

- **Streaming enumeration, one pass per directory.** `DirectoryStreamRegistry` keeps at most one open directory stream per active root, keyed by pass identifier and shared across every scanner instance in the process. A directory that fits one 512-name read is served in lexical order from that single read; a larger directory streams in native `readdir` order and never retains more than one batch of names. The lexical `afterName` cursor and the per-batch whole-directory reread (quadratic work across a wide directory) are gone. No native directory position is persisted: when a stream is lost (new process, eviction beyond 64 open streams, or a legacy cursor) only that unfinished pass restarts under a new identifier, and its superseded staging is invalidated exactly as a directory-change restart already was.
- **Bounded frontier.** Each root keeps a 64-directory in-memory window in its persisted progress. Directories discovered beyond the window are appended as `scan_frontier` rows (schema 14: `generation_id, root_path, directory_path, depth, sequence`, indexed by discovery order) in the same slice transaction as the staging they belong to; the store refills a draining window from those rows and records the remaining count as `pendingDirectoryCount`, so a root completes only when both are empty. Legacy progress blobs whose window exceeds the bound spill on resume. Invalidation of a directory pass also drops pending descendants; root restarts during pass validation, abandonment and publication delete the generation's rows. The lifecycle summary's pending-directory counter now counts window plus durable rows.
- **Budgeted continuation.** `PersistentMonitoringProbe.sample` continues unfinished detail in separately committed slices for up to two seconds of scan work (bounded to 256 slices), re-checking cancellation, the resource budget and the dirty-evidence fence before every slice, without another volume sample. Three consecutive slices without progress mark the observation stalled, add an explicit limitation, and make the lifecycle controller fall back to the configured interval; otherwise a continuing generation resumes after `min(5, max(0.5, elapsed))` seconds instead of four times the sample duration.
- **Schema guard.** A single `EvidenceStore.currentSchemaVersion` replaces four hard-coded version checks in shadow migration and open validation.

Publication remains one atomic reconciliation transaction over SQL sets; its size at one million files is measured below and left to TASK-532's headroom accounting.

At one million files the scan itself stays bounded (one stream, 892-byte progress, 90 MB in-process peak, 0.16 s worst slice) and staging commits stay small (about 4,800 entries per second), but the single atomic publication takes 150.6 s, writes a 2.98 GB write-ahead log, peaks the database family at 6.3 GB and leaves a 3.3 GB database, about 3.3 KB per file across staged payload, current state, bindings, events and history rows. The run needed the storage cap raised from the product default of 512 MiB to 4 GiB; under the default cap a million-file root is a live-state-too-large case that admission must refuse honestly. That refusal, headroom reservation before publication, and any bounded hidden preparation before a short fenced publication are TASK-532's contract, not claimed here.

The first attempt exposed a pre-existing publication defect that the research had only measured through a disposable "path-index" variant: `path_bindings` had no object-leading index, so the per-object revalidation in reconciliation scanned the whole table and publication was quadratic in file count. Schema 14 adds `path_bindings_object_path(object_id, path, valid_through)`; with it the product path publishes 100,000 files in 12.3 s. The fan-out run is the bounded-frontier proof: the in-memory window never exceeded 64 cursors and the persisted progress stayed under 7 KB while 99,873 pending directories lived in durable rows, with one open directory stream at a time and no re-enumeration or restart.

## Verification boundaries

Continuation is cooperative and bounded by wall time per sample; it does not preempt a slow filesystem call. The stall detector counts slices without processed entries, passes or status change; it does not diagnose why. Stream eviction beyond 64 open streams restarts passes for very wide fan-in of active roots. Publication is still one transaction; WAL growth at one million files is reported, not yet bounded. No installed app, live database or real watched roots were used; scale, overnight, rollback and packaged-app gates remain open.
